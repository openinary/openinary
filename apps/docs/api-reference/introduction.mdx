<Note>
  This reference documents a **self-hosted** instance. Openinary Cloud has its
  own base URL, authentication and endpoint set, see the [Cloud API
  Reference](/cloud/api).
</Note>

## Base URL

All endpoints are relative to your Openinary server URL.

```
http://localhost:3000   # default local setup
https://your-domain.com # self-hosted production
```

## Authentication

Protected endpoints require an API key passed as a Bearer token.

```http
Authorization: Bearer <your_api_key>
```

Generate API keys from the dashboard (`/api-keys`) or via the [API Keys API](/api-reference/api-keys/create). In API-only mode, the first key is printed to the server logs on startup.

<Note>
  Every API-key endpoint also accepts a dashboard session cookie, not just the
  API key management ones. That is how the dashboard calls storage, queue and
  upload without minting a key for itself.
</Note>

## Rate limiting

Public endpoints are rate-limited by IP address.

| Default                   | Configurable via                                       |
| ------------------------- | ------------------------------------------------------ |
| 100 requests / 60 seconds | `PUBLIC_RATE_LIMIT_MAX`, `PUBLIC_RATE_LIMIT_WINDOW_MS` |

Rate limit headers are included in every response:

| Header                  | Description                                    |
| ----------------------- | ---------------------------------------------- |
| `X-RateLimit-Limit`     | Maximum requests allowed in the current window |
| `X-RateLimit-Remaining` | Requests remaining in the current window       |
| `X-RateLimit-Reset`     | Unix timestamp when the window resets          |

Most API-key endpoints sit outside the public rate limiter, but not all: `POST /upload` and `GET /health/database` are behind it as well, so a burst of uploads can be throttled even with a valid key.

## Error responses

JSON errors carry a short `error` label and a `message` explaining it:

```json
{
  "error": "Bad request",
  "message": "Human-readable explanation"
}
```

<Warning>
  The media delivery routes (`/t/*` and `/authenticated/*`) return **plain
  text**, not JSON. Parsing every error body as JSON will throw on exactly the
  routes your users hit most. Check the response `Content-Type` first.
</Warning>

A few endpoints add fields on top of that pair. [Delete](/api-reference/storage/delete) returns a `details` object listing what was cleaned up, and [Invalidate Cache](/api-reference/cache/invalidate) returns an `errors` array. Neither is a general envelope.

| Status | Meaning                                                    |
| ------ | ---------------------------------------------------------- |
| `400`  | Bad request, invalid parameters or missing required fields |
| `401`  | Unauthorized, missing or invalid API key                   |
| `403`  | Forbidden, valid key but insufficient permissions          |
| `404`  | Not found                                                  |
| `409`  | Conflict, resource already exists                          |
| `429`  | Rate limit exceeded                                        |
| `500`  | Internal server error                                      |
